# Epic 21 Context: Monétisation en libre-service et engagement (P1b)

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Let an owner pay for their plan on their own (Mobile Money on Android, App Store on iOS) and have Keevo collect the payment and activate the plan's modules without super-admin action, with the entire commercial offer (plans, prices, trials, discounts) managed as data from the super-admin dashboard. In parallel, bring over Bref's engagement features — AI assistant, WhatsApp Business, client campaigns, client invoice portal — so a migrated Bref owner loses nothing. All AI goes through a single tool layer built on Keevo use cases, which is also exposed to external AI clients over MCP. This epic is part of the API parity required before the refonte go-live (milestone GL).

## Requirements & Constraints

- **Self-service payment**: a confirmed payment activates the plan's bundle and extends the expiry with no super-admin step. Port Bref's hardening: one pending checkout per tenant, atomic `INITIATING` lock on pay (recoverable after a timeout), transaction reference checked at OTP, credit read with a row lock, idempotent webhooks (deliveries can repeat), stale events ignored, sandbox subscriptions filtered in production, Apple grace period respected, `TRANSFER` and refund (refund means revocation) handled.
- **Migration continuity**: Bref webhooks (MyCoolPay, RevenueCat, Meta) and WhatsApp Business accounts must keep working before, during and after each owner's migration. A webhook for an owner Keevo doesn't know yet (still on api-bref) is ignored without error. The RevenueCat `app_user_id` of migrated owners stays valid because user UUIDs are preserved. Processed RevenueCat events are imported so nothing replays (24.5).
- **Account credit and SMS packs are real money**: they are kept, displayed and usable. Movements are append-only and the balance is never negative. Credit can be applied first to a plan payment if the owner chooses; pack consumption has a history (who, when, which counter) shown in "Mon plan" (done in 21.3).
- **Payments priced from the offer catalogue**: every paid path quotes through `subscription.api.OfferPricing.quote(tenant, plan, cycle, promoCode)` at initiation and stores the quote (base, discount, amount due); confirmation applies the stored price, never the current one. A zero quote is a free offer with no provider call. Promo-code uses are counted on confirmation (cap taken atomically). Confirmed payments write `tenant_payments.plan_code`/`cycle_code`. Done for Mobile Money (21.1), App Store (21.2) and credit/packs (21.3).
- **Offer as data**: no plan code, label, price, ceiling, quota, trial length or discount is hard-coded (Flyway seeds and a logged safe fallback excepted; this is a blocking review check). Bref's XAF price grid is seed data only. Every change is validated with French messages, audited (author, date, old and new value), and applies right away without redeploying the API or the app. Archiving a plan never affects the tenants already on it. A payment already started keeps the price shown when it started. Apple prices live in App Store Connect, so the configurable grid covers Mobile Money and granted plans; the Apple/grid gap per product is shown in the admin offer catalogue (done in 21.2).
- **AI**: guided topics are free (no model call, no credit). Free-text chat answers only by calling tools, never by generating or running SQL. Quota is charged once per question, never on a failure, and only one question can run per account at a time. Conversations are capped at 20 messages. The response shapes the Bref app consumes are kept. A parity corpus of at least 30 real questions with exact figures is an acceptance gate.
- **Isolation everywhere**: AI tools, the MCP server and the portal must refuse or filter exactly as the REST API does (tenant, module, role, employee scope). Each needs explicit isolation tests. The portal shows the bare minimum of fields per document.
- **Campaigns**: client campaigns target only clients with active marketing consent. Sending is async, with sent/delivered/failed tracking, and counts against quotas. Platform campaigns target tenant segments over push, WhatsApp, SMS and email, and are audited.
- **WhatsApp**: WABA tokens are encrypted at rest. Meta webhook signatures (`X-Hub-Signature-256`) are verified. The template approval cycle and the 24 h window are respected. Invoices and quotes go out from the owner's WABA number (`bref_facture` template), never the platform number, with platform free text as the fallback.
- **Transverse**: no technical data (UUIDs, raw codes) in user-facing output, French labels only. Flutter V1 2.0.x compatibility on `/api/v1` (no `null` where V1 expects a value). Core writes (POS sale, payment) are never blocked by quota.

## Technical Decisions

- **New modules** follow the existing registry: manifest, `db/modules/<id>/`, per-role permissions, `@RequiresEntitlement`, `DeltaEntityProvider` where synced. The registry modules are `ai-assistant`, `whatsapp-cloud` (BUSINESS), `client-portal` (platform/global), and the paid `mcp-access`. `payments` (21.1) is a backend Modulith module holding public platform data only (no manifest, no tenant DDL).
- **Activation path**: payments apply the plan in one transaction through `PlanAdministrationPort.changePlan` (subscription row, public plan, `tenant_plan_events`, paid-module rows) with cause `SELF_SERVICE_PAYMENT` (`EXPIRY` returns to the free plan only if the plan is still that subscription's grant). Patterns established by 21.1–21.3, to reuse in 21.5 and later: provider behind a strategy port (real / sandbox / disabled by config, fail-fast validation; fake in tests); state machine with guarded single-statement transitions (`payment_requests`, one in-flight request per tenant via partial unique index; `external_subscriptions.status` ordered by `last_event_ms`, stale events dropped); idempotent consumer = claim row inserted in the same transaction as the effects (no claim/release); webhook authenticated (signature or constant-time secret, none configured = everything refused); unknown reference answered OK and ignored; command dispatch by event type; owner notices via after-commit listener (`@DeliverOnce`). Ledger writes go to `tenant_payments` (method `MOBILE_MONEY` / `APP_STORE`, unique `store_transaction_id`, `plan_code`/`cycle_code`). The App Store product → plan × cycle mapping (`store_products`) is offer data owned by `subscription.offer`, read by `payments` through the `StoreProducts` port. New global tables live in `public`, tenant data in `kv_x` schemas.
- **Quotas** reuse `public.usage_counters` from 19.8 with an atomic single-statement increment. Purchased packs are consumed after the monthly quota.
- **AI tool layer (21.8, done, decision D8)**: AI reaches data only through read-only `@Tool` methods (Spring AI 1.1.8, `spring-ai-model` only — the Boot 3.5 line; 21.4/21.9 add their model/MCP starters on the same `spring-ai-bom`). One `{Module}McpTools` `@Component` per module in `adapter/in/mcp/` mirrors a REST read handler (same `@PreAuthorize`/`@RequiresPermission`/`@RequiresEntitlement(READ)`, same store/employee scope helpers), builds the `…Query` itself, takes no tenant/actor/role parameter, returns bounded French results (≤ 50 rows, `truncated`/`hasMore`) with no technical id except `storeId` (chaining key, never to be displayed). `shared.ai.AiToolRegistry` lists the tools the session may call, calls one by name with JSON args through the bean proxy (REST gates run), maps failures to the REST French messages, caps results at 64 KB, audits every call in `public.ai_tool_calls`, and hands Spring AI `ToolCallback`s via `allowedToolCallbacks(channel)`. `AiToolCoverageTest` enforces the rules and regenerates `docs/ai/tools.md` (catalogue of the 16 tools). The registry reads actor and tenant from the calling thread (`SecurityContextHolder`, `TenantContext`) and limits nothing. Any future write tool needs explicit user confirmation. Bref's SQL query builder is never ported.
- **AI assistant (21.4)**: module `ai-assistant`, same operations and response shapes as Bref (`POST /v1/ai/chat`, conversation CRUD, bulk delete; contract in `keevo/contracts/`), conversations in `kv_x.ai_conversations`. Guided topics are served by 21.8 tools or existing stats endpoints, free. Free text: configurable provider (OpenAI / Gemini / Ollama, ported from Bref) receives the question plus only `allowedToolCallbacks` for this user, answers in French from tool results; AI quota (daily/monthly, `usage_counters`) charged once per question, never on failure; one question in flight per account. Tool calls must run on the request thread (non-streaming tool execution) or propagate both security and tenant contexts. The system prompt forbids showing identifiers and the rendered answer is filtered so no UUID reaches the app.
- **External MCP server (21.9)**: Spring AI over HTTP/SSE, behind the paid module `mcp-access` (not entitled = `MODULE_NOT_ENTITLED`, no data). Authentication by owner-created personal tokens (revocable, restricted to chosen tools, expiring); revocation is immediate (same mechanism as 16-11 sessions). Same controls as 21.8, calls count against the tenant AI quota. For each request the transport binds the token owner's authentication (same shape as the JWT filter: principal, role, store details) and tenant before calling the registry, and clears them after (no leak across pooled threads); rate limit per token and per tenant (429 in French, no data).
- **Client portal**: global `public.portal_clients`, separate from merchant accounts, with OTP login from 19.2. `public.invoice_phone_index(phone_normalized, tenant_id, invoice_id)` is fed at issue and at import. Each document is read from its own tenant's schema. A per-tenant switch turns the portal off.
- **WhatsApp**: one Meta webhook per Meta app, routed to the tenant by `phone_number_id`. The platform WhatsApp provider and the per-tenant WABA module coexist. Bref's providers take priority (Meta Cloud, MboaSMS/Infobip, Resend, Expo).
- **Performance rule (mandatory)**: pick the right pattern; no N+1, set-based SQL, keyset pagination, an index for every new filter/join/sort, batched fan-out for campaigns. Each spec states its pattern and hot-path complexity.
- **Scope of this repo**: backend only. Each spec needs a mobile section (the RN app lives in the Bref repo) and a "Dashboard super-admin (autre dépôt)" section for every admin feature. The offer catalogue must be fully editable from the dashboard (no read-only screens). API contracts go in `keevo/contracts/`.

## UX & Interaction Patterns

- "Mon plan" shows the plan, expiry, quotas, credit and pack balances, the current prices and any discount (struck-through price, promotion end date), all read from the API. Payment is Mobile Money on Android (USSD/OTP, the API returns the next step) or in-app purchase on iOS. On confirmation, modules activate without a restart and the owner is notified.
- The AI assistant offers guided topics (diagnostic, revenue, unpaid, collections, sellers, stores, clients; period, comparison, store → sellers drill-down, unpaid call list) plus free text. Errors return clear French messages.

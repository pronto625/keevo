## Deferred from: code review of v1s-12-2-session-revocation-5min (2026-07-21)

- **`iat` futur / pas d'upper-bound de clock-skew** [`JwtAuthFilter.java:141`] — Pas de `setAllowedClockSkewSeconds` au parse ; un `iat` futur biaisé traite un token minté avant révocation comme post-révocation (accepté). RS256 empêche le forgage mais un skew légitime multi-région crée une petite fenêtre. Partiellement mitigé par le patch granularité-seconde. Refonte : adopter une politique de clock-skew (jjwt `setAllowedClockSkewSeconds` + reject `iat` loin dans le futur).
- **Cache `ConcurrentHashMap` non borné** [`CachedTokenRevocationAdapter.java:40`] — Pas d'éviction ni de size cap ; les entrées `(userId,tenant)` persistent pour la durée de vie JVM (users dormants/supprimés, tenants churned). La claim spec « bounded by active pairs » est fausse. Fuite mémoire lente. Refonte : Caffeine `expireAfterWrite(5min).maximumSize(...)` ou sweeper périodique.
- **Race de re-population de cache stale (read-then-put non atomique)** [`CachedTokenRevocationAdapter.java:54-55`] — Thread A (cache miss) lit l'ancien tva via delegate, puis avant `cache.put` le Thread B exécute `revokeAllSessions` (DB update + `cache.remove`) ; le Thread A réinsère alors l'ancien tva avec un `fetchedAt` frais → cache stale servi jusqu'à TTL sur la MÊME instance qui a révoqué. Fenêtre minuscule, requiert une requête concurrente du principal révoqué au moment exact de la révocation. Refonte : `computeIfAbsent`/`compute` atomique ou tombstone.
- **Cache stampede / thundering herd sur miss** [`CachedTokenRevocationAdapter.java:49-55`] — Check-then-put non atomique ; N requêtes concurrentes sur un cache miss chaud déclenchent chacune un `SELECT m.tokens_valid_after`. Idempotent (pas de défaut de correction), mais contrecarre l'objectif de protection DB juste sous charge burst. Refonte : coalescence des loads (`ConcurrentHashMap<String,CompletableFuture<Instant>>`).
- **`shouldCallDelegateOnCacheExpiry` n'exerce pas l'expiry TTL** [`CachedTokenRevocationAdapterTest.java:42-60`] — Le test admet utiliser une clé différente (« TTL is real-time, not mockable ») au lieu d'avancer le TTL ; la branche `cached.fetchedAt().plusSeconds(TTL_SECONDS).isAfter(now)` n'est jamais exécutée. Fausse couverture AC7 (cache expiré >TTL → delegate rappelé). Un bug d'arithmétique TTL passerait. La logique production est triviale et correcte à l'inspection. Refonte : injecter un `java.time.Clock` dans `CachedTokenRevocationAdapter` pour rendre le TTL testable (avancer le temps dans le test et ré-querier la MÊME clé).
- **`JdbcTokenRevocationAdapterTest` utilise `anyString()` et contourne le `RowMapper`** [`JdbcTokenRevocationAdapterTest.java:25-44`] — `when(jdbcTemplate.queryForObject(anyString(), any(RowMapper.class), ...)).thenReturn(now)` retourne un `Instant` pré-construit, donc le `RowMapper` réel (`rs.getTimestamp("tokens_valid_after").toInstant()`) ne tourne jamais et la string SQL n'est pas assertée. Un rename de colonne ou une mauvaise table casserait le runtime tout en gardant les tests GREEN. Refonte : `ArgumentCaptor<RowMapper>` invoqué sur un `ResultSet` mocké (`when(rs.getTimestamp("tokens_valid_after")).thenReturn(...)`) + `eq(SELECT_TVA)`.
- **Champ `log` inutilisé (dead code, zéro observabilité)** [`CachedTokenRevocationAdapter.java:32`] — `private static final Logger log` déclaré, jamais référencé. Pour un contrôle de sécurité avec fenêtre de propagation 5min, aucun événement d'invalidation/miss/race-stale n'est observable. Refonte : `log.debug` sur cache miss + invalidate (au minimum), DEBUG sur stale-race.
- **Tests manquants : path `tva==null` et frontière `iat==tva`** [`JwtAuthFilterTest.java:345-408`] — Seuls `iat<tva` (reject) et `iat>tva` (allow) couverts. Manquent : (a) `getTokensValidAfter` retourne null → check skippé, requête procède (path dominant pour tout user non révoqué) ; (b) `iat == tva` (AC2 stipule `>=` → allow ; le code utilise `isBefore` strict `<` donc l'égalité est acceptée — correct mais la charnière de contrat n'est pas gardée). Un futur refactor vers `!iat.isAfter(tva)` (`<=` → reject) violerait AC2 en passant les tests existants. Refonte : ajouter `shouldAllowWhenTokensValidAfterNull` + `shouldAcceptTokenWhenIatEqualsCutoff`.
- **Latency OWNER : check révocation DB per-request sur cache miss** [`JwtAuthFilter.java:138`] — Le rôle OWNER avait 0 hit DB dans le filtre ; la story 12.2 ajoute un `SELECT m.tokens_valid_after` (toutes les 5min/user sur cache miss). By-design — le cache absorbe l'essentiel. Refonte : envisager un JOIN unique avec le check EMPLOYEE `queryForMap` pour mutualiser le round-trip.

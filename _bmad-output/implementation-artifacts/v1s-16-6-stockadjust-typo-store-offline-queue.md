# Story 16.6: Typo `STOCK_ADJUST` mouvement local + store offline sync_queue (FR27, FR30)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Toor,
I want local stock-adjustment movements typed correctly (`ADJUSTMENT`, not `STOCK_ADJUST`) and offline store writes reliably queued for sync,
so that the "Ajustements" filter in the movement history actually shows locally-created adjustments, and a boutique created/modified/deactivated while offline is not silently lost — it reaches the backend once connectivity returns (FR27, FR30).

## Acceptance Criteria

**Part A — `STOCK_ADJUST` movement-type typo**

1. **Given** `stock_repository_impl.dart:259` writes the local `StockMovementModel.movementType` as `'STOCK_ADJUST'` while every consumer of that field (`stock_history_page.dart:178/276` filter+label switch, `stock_movements_table.dart:18` schema comment, `validate_inventory_provider.dart:140` sibling write-site) uses `'ADJUSTMENT'`, **when** a stock adjustment is recorded offline (or online — the local write path is unconditional per Story 5.6), **then** the "Ajustements" filter in `StockHistoryPage` does not match the locally-inserted row until it is later overwritten by the synced-back remote copy (which the backend always writes as `ADJUSTMENT` — see `AdjustStockUseCase` `MovementType.ADJUSTMENT`), and the row's label falls through to the raw string `'STOCK_ADJUST'` instead of `'Ajustement'` in the interim.
2. **Given** AC1, **when** fixed, **then** `_adjustStockLocally()` (`stock_repository_impl.dart:243-290`) sets `movementType: 'ADJUSTMENT'` on the `StockMovementModel` it inserts (line 259) — **and only that field**.
3. **CRITICAL — do NOT touch the sync operation string.** The `_syncService.queueOperation(operation: 'STOCK_ADJUST', ...)` call at line 279 (a **different, unrelated string** — the wire `operationType` sent to `POST /api/v1/sync/push`) **must stay exactly `'STOCK_ADJUST'`**. The backend's `StockAdjustSyncHandler.supportedTypes()` (`keevo/backend/.../handler/StockAdjustSyncHandler.java:30`) is a hardcoded `Set.of("STOCK_ADJUST", "RECORD_STOCK_ENTRY")` — renaming the queued operation to `'ADJUSTMENT'` would make the backend return `REJECTED`/`UNKNOWN_OPERATION_TYPE` for every offline stock adjustment forever (see Dev Notes — this exact mistake is the #1 risk in this story).

**Part B — Store offline writes bypass `sync_queue`**

4. **Given** `StoreRepositoryImpl` (`store_repository_impl.dart`) follows the architecturally-correct **Backend-First-When-Online** shape for `createStore()`/`updateStore()`/`deactivateStore()` (try remote first; `architecture.md` explicitly marks all three as `✅ Backend-first — Remote first, offline local fallback`), **when** the remote call fails with a **network** error (not a business `StoreException` like `PLAN_LIMIT_EXCEEDED`/`WAREHOUSE_ALREADY_EXISTS`, which are re-thrown to the UI unchanged), **then** today the `catch` block only performs an optimistic local Drift write (`_local.upsert(...)` / `_local.deactivate(...)`) — no `sync_queue` entry is ever created, so the change is **never pushed to the backend**, is invisible to other devices/employees, and is **permanently lost** if the app is reinstalled or the local DB is cleared (`store_repository_impl.dart:36-117` — no `SyncService`/`SyncTriggerDispatcher` dependency exists at all today).
5. **Given** AC4, **when** fixed, **then** each of the three offline-fallback branches also calls `SyncService.queueOperation(operation: 'CREATE_STORE'|'UPDATE_STORE'|'DEACTIVATE_STORE', payload: {...}, entityId: storeId)` followed by `SyncTriggerDispatcher.triggerPushIfIdle()` — mirroring the `queueOperation`/`triggerPushIfIdle` call shape already used by `ClientRepositoryImpl`/`SupplierRepositoryImpl` (`CREATE_CLIENT`/`UPDATE_CLIENT`/`ARCHIVE_CLIENT` naming convention) — **without** adopting those repos' *unconditional local-first control flow* (see Dev Notes — "mirrors clients/suppliers" scopes to the queueing mechanism only, not the online/offline branching shape, which `architecture.md` already certifies as correct for stores).
6. **Given** AC5's offline `createStore()` path currently generates a non-UUID placeholder id (`'local-${now.millisecondsSinceEpoch}'`, e.g. `'local-1737991234567'`), **when** fixed, **then** it instead generates a real client-side UUID (`const Uuid().v4()`, matching `ClientRepositoryImpl.create()`/`SupplierRepositoryImpl.create()`) — required because the new backend handler parses the queued `id` with `UUID.fromString(...)` and would crash on the old placeholder format.
7. **Given** AC5 queues operation types with **no existing backend handler** (`grep` for `CREATE_STORE`/`UPDATE_STORE`/`DEACTIVATE_STORE` across `keevo/backend/src/main` returns nothing before this story), **when** the queued operation is pushed, **then** without a handler `SyncPushService.processOperation()` (`SyncPushService.java:157-167`) returns `REJECTED`/`UNKNOWN_OPERATION_TYPE`, and `RestSyncService.push()` (`rest_sync_service.dart:106-113`) leaves the entry in `sync_queue` and **increments `retryCount` forever** — this is not a cosmetic gap, it's a **global regression**: `hasPendingOperations()` (`rest_sync_service.dart:146-153`) counts **all** unsynced `sync_queue` rows with no type filter, and several repositories (`StockRepositoryImpl.getLevels/getMovementHistory`, others) gate their remote-refresh-into-local-cache logic on `!hasPendingOperations()` — a single permanently-stuck store operation would silently freeze remote refresh for those repos indefinitely. **Therefore this story also adds the two missing backend sync handlers** (`CreateStoreSyncHandler`, `StoreSyncHandler` for `UPDATE_STORE`/`DEACTIVATE_STORE`) — see Tasks. This is a deliberate, justified expansion beyond the epic's "100% Flutter" framing (flagged for PO awareness at the end of this story, not a blocker to implementation).
8. **Given** AC7's new handlers, **when** implemented, **then** `CreateStoreSyncHandler` mirrors `CreateClientSyncHandler.java` exactly: bypasses `CreateStoreUseCase` (which would discard the client-generated UUID and also enforce plan-limit/warehouse-uniqueness checks that this offline path has never enforced — same posture as `CreateClientSyncHandler` skipping `CreateClientUseCase`, not a new gap), writes `Store` directly via `StoreRepository.save()` preserving the client UUID, and is **idempotent** (`storeRepository.findById(id).isPresent()` → return `APPLIED` without re-inserting). `StoreSyncHandler` mirrors `ClientSyncHandler.java`: `UPDATE_STORE`/`DEACTIVATE_STORE` call the existing `UpdateStoreUseCase`/`DeactivateStoreUseCase` unchanged. Both handlers add an OWNER-only guard (`if (!isOwnerRole()) throw new DomainException(ErrorCode.FORBIDDEN, ...)`), mirroring `TransferSyncHandler`'s guard added in Story v1s-12-8 and `StoreController.requireOwner()`'s existing REST-path defense-in-depth.
9. **Given** AC7-8, **when** implemented, **then** `ConflictStrategyRegistry.LWW_OPS` (`ConflictStrategyRegistry.java:20-25`) gains `CREATE_STORE`, `UPDATE_STORE`, `DEACTIVATE_STORE` (last-write-wins, same treatment as `UPDATE_CLIENT`/`ARCHIVE_CLIENT`), and the pre-existing **orphaned, unused** `"STORE_UPDATE"` entry (dead — no handler has ever supported that exact string; a leftover from Story 3.1 planning) is corrected to `"UPDATE_STORE"` to match the handler's actual `supportedTypes()`.
10. **Given** AC4-9, **when** all fixes are applied, **then** the existing synchronous online-path behavior is **completely unchanged**: `createStore()`/`updateStore()`/`deactivateStore()` still try remote first; `StoreException` business errors (`PLAN_LIMIT_EXCEEDED`, `WAREHOUSE_ALREADY_EXISTS`, `STORE_NOT_FOUND`) are still re-thrown synchronously to the UI exactly as today (`store_repository_impl_test.dart`'s `'createStore() rethrows StoreException.planLimitExceeded'` test must still pass unmodified); only the network-failure `catch` branches gain the queue call.

## Dev Notes

- **Two independent, unrelated bugs bundled in one story** per the epic (ties Story 13.4's "same pattern applied to store offline writes" note). Part A is a 1-line Flutter fix. Part B is a Flutter fix **plus** a small, justified backend addition (see AC7-9) — read that reasoning before starting, it changes the shape of the fix from what the epic text alone implies.
- **Part A — the trap:** `stock_repository_impl.dart` has TWO different `'STOCK_ADJUST'` strings 20 lines apart (259 and 279) that look related but serve completely different purposes: one is the **local Drift row's movement-type label** (must become `'ADJUSTMENT'` to match every reader of that field), the other is the **wire protocol operation type** sent to the backend (must stay `'STOCK_ADJUST'` — the backend's `StockAdjustSyncHandler.supportedTypes()` is a literal `Set.of("STOCK_ADJUST", "RECORD_STOCK_ENTRY")`, confirmed by reading the actual handler source, not just the Flutter side). Changing both would silently break offline stock-adjustment sync entirely — the backend would reject every one with `UNKNOWN_OPERATION_TYPE`, forever, with no error surfaced to the user (see `rest_sync_service.dart` REJECTED handling — retryCount increments, entry stays queued). This is exactly the kind of same-string-different-meaning trap this Dev Notes section exists to catch.
- **Part B — why the fix is NOT "make StoreRepositoryImpl exactly like ClientRepositoryImpl":** the epic AC says "mirrors clients/suppliers", and `ClientRepositoryImpl`/`SupplierRepositoryImpl` are **unconditionally local-first** (no remote call at all in `create()`/`update()`, per their `Story 5.6` doc comments) — but `architecture.md`'s module audit table (`architecture.md:838-844`, section "✅ CONFORMANT") explicitly certifies `StoreRepositoryImpl.createStore()/updateStore()/deactivateStore()` as `✅ Backend-first — Remote first, offline local fallback`, i.e. the **opposite** shape, and marks it as needing **no** control-flow changes. Cross-referencing both documents: the correct reading is "mirrors clients/suppliers" = reuse the **`queueOperation`/`triggerPushIfIdle` mechanism and `CREATE_X`/`UPDATE_X`/`ARCHIVE_X`-style naming**, not the unconditional-local-first branching. Keep `StoreRepositoryImpl`'s existing remote-first `try`, keep the synchronous `StoreException` rethrow (this is a real, tested, user-facing contract — `PLAN_LIMIT_EXCEEDED`/`WAREHOUSE_ALREADY_EXISTS` must still surface immediately when online), and only add the missing queue call inside the three `catch` blocks. **Caveat:** `architecture.md`'s audit table is not fully trustworthy either — it describes `ClientRepositoryImpl.create()` as "✅ Backend-first — Try remote, catch → local fallback", which **contradicts the actual current code** (unconditionally local-first, no remote call). Treat the actual `.dart` source as ground truth over this doc when the two disagree; the doc was cited above only for the specific claim about **Store's own** shape, which is corroborated by reading `store_repository_impl.dart` directly.
- **Part B — the backend-handler scope decision (flag for PO):** the epic frames Epic 16 as "100% Flutter, aucune contrepartie backend" and tags this story `[A/C]`. Taken 100% literally, Part B would be Flutter-only: just add the `queueOperation` calls. But doing *only* that, with no backend handler for `CREATE_STORE`/`UPDATE_STORE`/`DEACTIVATE_STORE`, means every queued store operation gets `REJECTED`/`UNKNOWN_OPERATION_TYPE` on every push attempt, **forever** — the fix would look complete (code compiles, queue entry exists) but silently never accomplish its own stated goal ("so that offline store changes sync"). Worse, per AC7, a perpetually-`REJECTED` entry poisons the **global** `hasPendingOperations()` check that gates remote-refresh in unrelated repositories (confirmed: `StockRepositoryImpl.getLevels()`/`getMovementHistory()` both skip their remote-refresh block `if (!await _syncService.hasPendingOperations())`). This story therefore adds the two small backend handlers (Tasks 3-4) — each is a ~40-60 line mirror of an existing handler wired to already-existing use cases/repository methods, low risk, no new business logic. **If the PO wants strict Flutter-only scope for `[A]`-tagged hotfix stories, defer Tasks 3-5 to a follow-up backend story** and, if so, the Flutter fix alone should NOT be considered AC7-8 complete — note this explicitly in the completion notes rather than silently shipping a non-functional queue.
- **Idempotency and validation posture for `CREATE_STORE`:** `CreateStoreSyncHandler` bypasses `CreateStoreUseCase` entirely (like `CreateClientSyncHandler` bypasses `CreateClientUseCase`) — this means **plan-limit and warehouse-uniqueness checks are not enforced for offline-created stores**, same as they are not enforced today (the existing offline-catch branch has zero validation). Not a new gap introduced by this story; just don't try to "fix" it by calling `CreateStoreUseCase` from the handler, which would discard the client-generated UUID needed for idempotent replay (exactly the reason `CreateClientSyncHandler`'s own doc comment gives for bypassing `CreateClientUseCase`).
- **RBAC guard convention:** Story v1s-12-8 (`42f3bef`, most recent related commit) added `isOwnerRole()`/`extractAssignedStoreId()` to `AbstractSyncOperationHandler` specifically to close RBAC bypasses on `/api/v1/sync/push` for 4 existing handlers. New handlers that manage OWNER-only resources must self-guard the same way (`TransferSyncHandler`'s exact pattern, cited in Task 3/4) — the sync-push endpoint has no per-operation-type `@PreAuthorize`, only handler-level checks.
- **No changes to `RemoteStoreDataSource`, `LocalStoreDataSource`, `StoreController`, `CreateStoreService`/`UpdateStoreService`/`DeactivateStoreService`, `Store`/`StoreType`/`StoreFactory` domain classes, or any REST DTO** — this story only touches the offline-fallback branch of the repository and adds new sync-push handlers that reuse existing use cases/ports.

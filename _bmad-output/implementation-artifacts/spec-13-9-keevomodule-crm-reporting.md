## Intent

**Problem:** The socle (13.1–13.8) works on manifests and annotations, but no real module implements the `KeevoModule` contract (spec-socle §4.1) and nothing validates the whole chain — module migrations, lifecycle hooks, capability, event consumption, per-tenant on/off — on existing code before the pilot module (Epic 14) (MOD-FR1, MOD-NFR8).

**Approach:** Introduce `KeevoModule` with lifecycle hooks invoked by 13.8a, programmatic capability registration, and per-tenant gating of event listeners; convert CRM (provider) and Reporting (consumer) to it without changing their behaviour for current tenants.

**Decisions (autonomous run, user delegated all choices 2026-10-28):**
- **`KeevoModule`** (published, `com.keevo.shared.module`): `String id()`; `default void onActivate(ModuleTenantContext ctx) {}`; `default void onDeactivate(ModuleTenantContext ctx) {}`; `default void registerCapabilities(CapabilityRegistrar registrar) {}`; `default void registerExtensions(ExtensionRegistrar registrar) {}`. `ModuleTenantContext(String tenantSchema, String tenantCode, ActorRef actor)` — no HTTP/Spring-web types. **The manifest stays JSON-only**: `KeevoModule` has no `manifest()` builder; `ModuleRegistry.definition(id())` gives it (routed 13.1: Java-built manifests can't bypass the loader). In addition `ModuleManifest`'s compact constructor enforces its own invariants (id pattern, non-blank display name, lists non-null and immutable) so a hand-built instance cannot be invalid.
- **Discovery/validation at boot**: one `KeevoModule` bean per id at most; its id must be an installed manifest; a manifest may have no bean (modules not yet converted keep working).
- **Lifecycle hooks**: `ModuleLifecycleService` (13.8a) calls `onActivate` for each activated step after its provisioning, and `onDeactivate` after the DISABLED write, inside the same transaction; a hook exception rolls the call back (`MODULE_ACTIVATION_FAILED`-style French error, no technical detail).
- **Programmatic registration**: `CapabilityRegistrar.provide(Class<T extends Capability>, T impl)` / `ExtensionRegistrar.contribute(Extension)`; collected at boot into the same registries as the annotations (13.6/13.7) with the same validation (manifest `provides`/`fills` cross-check, duplicates, autowire exclusion rule unchanged). CRM moves `ClientLookupPort` to `CrmModule.registerCapabilities` (annotation removed from the adapter) — one path per capability.
- **CRM migrations**: `db/modules/crm/V1__crm_baseline.sql` reproduces the current tenant DDL of `clients`, `suppliers`, `product_suppliers` (columns, defaults, indexes, constraints) **idempotently** (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, constraints guarded in `DO $$` blocks) — a no-op on every existing tenant (prod data untouched). `TenantSchemaProvisioner` keeps creating these tables for now (the `sales.client_id` FK needs `clients` before `sales` at registration — ordering constraint); `TenantSchemaSyncService` stops mirroring the three CRM tables (module migrations own their evolution from now on). Removing them from `TenantSchemaProvisioner` is routed with 16.5 (FK ordering noted).
- **Provisioning of free modules with migrations**: at tenant registration (after the core DDL) and at boot (`provisionAll` for every installed free module with migrations, live tenants, after `TenantSchemaMigrationRunner`, failures logged per tenant code and boot continues), so every tenant gets `flyway_history_crm` at V1 — the only effect on existing prod tenants is that metadata table.
- **Migration policy (routed 13.4)**: manifest `ID_MAX` 48 (history table ≤ 63 chars, checked at load); `validateOnMigrate` stays on, `outOfOrder` off — an edited applied script fails provisioning loudly (repair = new versioned script; manual `flyway repair` procedure documented); `core` has no migrations (nothing to track) — documented.
- **Reporting**: `ReportingModule implements KeevoModule` (no capability). Event listeners of a module are gated per tenant: a new `@ModuleScoped("<id>")` annotation on listener classes/methods; the existing listener interceptor (12.4 `ModuleListenerInterceptor`, which binds the tenant) and an equivalent wrapper for synchronous `@TransactionalEventListener`s skip the invocation (publication completed, DEBUG log with tenant code) when the module is DISABLED for the event's tenant; READ_ONLY still runs (reports are reads of past data). Apply to every reporting listener (`EndOfDayReportListener`, report generators). Validation: `@ModuleScoped` id must be installed.
- **Not here**: relocating sync handlers into their modules (impossible while `sync → crm :: api` exists — routed to 14.3, which removes that edge), owner self-service, Flutter.

## Boundaries & Constraints

**Always:** zero behaviour change for current tenants (all modules active); CRM V1 is a no-op on existing schemas (verified on a copy of `keevo_dev` tenants and on a fresh tenant); all test packages green; architecture suite green; prod-classpath profile green.

**Never:** no `DROP`, no data change, no removal of CRM DDL from `TenantSchemaProvisioner` yet, no deploy.

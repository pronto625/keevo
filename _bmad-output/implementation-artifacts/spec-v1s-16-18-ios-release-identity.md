## Intent

**Problem:** The iOS Runner generated in 16.2 still carries the Flutter template identity: bundle id `com.example.keevo` (Apple refuses `com.example`), default Flutter icons and launch image, and one `Runner.entitlements` with `aps-environment=development` for every configuration. The Android `applicationId` is the same template id, but its Firebase app (`google-services.json`) is registered only for it.

**Approach:** Apply the production id `com.keevo.keevo` to iOS now. Prepare (but do not run) the Android switch behind a documented Firebase procedure and a dry script. Generate brand iOS icons and a sober themed launch screen from the existing brand icon. Keep orientations aligned with Android. Split the entitlements per configuration.

## Boundaries & Constraints

**Always:**
- Production reverse-DNS id = `com.keevo.keevo` (architecture.md: `flutter create --org com.keevo --project-name keevo`). RunnerTests = `com.keevo.keevo.RunnerTests`.
- Plists (Info.plist, both entitlements) stay valid XML plists (checked with Python `plistlib`). Edit `project.pbxproj` by hand and re-read it. Every new object id is a unique 24-hex id.
- iOS app icons are opaque (no alpha), full-bleed square, and come from the brand source `assets/icon/icon_light.png`. They are generated by `flutter_launcher_icons` (`ios: true`, `remove_alpha_ios: true`) from an iOS-specific square derivative.
- Launch background colours = the app scaffold colours from `AppTheme` (light `scaffoldLight` #F8F9FA, dark `darkSurface` #0D1B2A), defined as an asset-catalog named colour with a dark appearance.
- Bump `keevo/app/pubspec.yaml` version 1.1.39+38 → 1.1.40+39.

**Never:**
- Change Android `applicationId`/`namespace`/Kotlin package or `google-services.json` in this story. Running the switch script is the user's job after the Firebase step.
- Regenerate Android or web launcher icons (revert any incidental change made by the generator).
- Run `flutter build`, `flutter clean`, Xcode tools or `plutil` (Linux host).

## Design Notes

Orchestrator decisions (2026-10-13), recorded:
1. Production id `com.keevo.keevo` (architecture.md org `com.keevo`), applied to iOS now.
2. Android stays `com.example.keevo` until the user registers `com.keevo.keevo` in Firebase. Changing it now would break the `google-services` Gradle plugin, which finds no client for the package. A new applicationId is also a different app on the device, so testers must uninstall and reinstall. The epic item is ticked as "décidé, bascule Android en attente de l'action utilisateur Firebase".
3. Icons from the existing brand icon. Launch screen sober, in theme colours.
4. Entitlements split per configuration instead of relying on the Xcode export rewrite.

Implementation decisions:
- **Profile → development (deviation from the decision-4 wording "Release/Profile → production").** Profile builds (`flutter run --profile`) are installed on a device with automatic *development* signing. A development provisioning profile carries `aps-environment=development`, and Xcode rejects an entitlements value that disagrees with the profile. Only Release is archived and exported with the App Store / Ad Hoc distribution profile, so Release alone gets `production`. A local `flutter run --release` with automatic development signing may therefore hit the same mismatch; that case is in the manual checklist (use Profile for on-device performance runs).
- **Orientation:** Android has no `screenOrientation` lock, so it rotates. iPhone already allows Portrait + LandscapeLeft/Right (no upside-down, like Android phones), and iPad allows all four (Apple requires it for multitasking unless `UIRequiresFullScreen`). Matching Android therefore means no change. The test pins the parity: if Android gets locked to portrait later, the test fails until iOS follows.
- **iOS icon source:** `flutter_launcher_icons` squashes non-square images, and the light source has white corners plus a bottom shadow. Under iOS's own rounded mask those would show as white slivers. A full-bleed 1024 derivative avoids that. Android/web keep `icon_light.png` (out of scope).
- **Deployment target 13.0 vs PRD "iOS 14+"** -- reject, no change: 13.0 is the Flutter 3.41 template floor. Supporting iOS 13 is a superset of the PRD target and it does not affect store identity.
